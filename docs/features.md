# Feature matrix (vs. Blender)

This editor follows Blender's workflow, naming and keymap: operator ids (`mesh.extrude_region_move`),
property names (`rotation_euler`, `bevel_depth`, `energy`) and data paths
(`pose.bones["Arm"].rotation_euler`, `constraints["Track To"].influence`) are Blender's, and so is
the coordinate system (Z up, meters, radians).

Every action is an operator in one registry ([architecture](architecture.md#operators)): about 260
operators in `packages/core/src/operators`, plus about 40 UI-only ones (view navigation, dialogs,
modal tools) registered by the web app. Apart from those UI-only actions, whatever a menu, hotkey or
panel does (panels edit fields through `data.set_property` and the feature operators) can also be
done from the F3 search, from the JavaScript console (`ops(id, params)`) and by MCP agents
(`run_operator`, `batch`); many features are reached only that way. Operators reject unknown or
misspelled parameters, and `registry.describe()` (console) or `list_operators` (MCP) return every
operator's JSON schema.

Legend: ✅ implemented · 🟡 partial (the differences are listed) · ❌ not implemented. "Operator
only" means there is no menu entry or panel for it in the web UI yet.

Move, Rotate and Scale change an object's channels as Blender's do and store only the channels they change, the others stay exactly as they were: a Move only the location, a rotation only the rotation and a scale only the scale, each also the location when it moves the object's origin (about another pivot than the origin: the 3D cursor, the median point or the bounding box center of several objects, with Active Element the active object when it is another one, selected or not). A selected object whose parent is selected too only follows its parent and counts for neither the median point nor the bounding box center, except that a rotation about Individual Origins also turns it about its own origin, as in Blender (it does not count for the rotation center then either: Blender's TD_NOCENTER); auto keying keys every object a transform transforms with the values it shows afterwards, also one it leaves as it was (a rotation by 0 keys all nine channels and writes none), as Blender does. Without auto keying a channel the transform changes that is already animated (keyed, its F-curve not muted, not set by a driver) is keyed at the current frame with its new value, so the object stays where it is moved, as the editor's other tools keep edits of animated channels; Blender keeps such a change without a key only until the frame changes, which this editor has no state for. A channel a driver sets keeps the value its driver gives, in the preview too. The Snap menu, `object.transform_set` and Clear Location, Rotation and Scale (Alt+G, Alt+R, Alt+S) key the same way (with auto keying the Snap menu keys the location and each Clear its own channel, as Blender's do). Transforms work on what the scene shows at the current frame, as in Blender: an object parented to a bone moves, turns and scales in the bone's posed axes, the child of an animated, posed or constrained parent in its parent's evaluated axes, and an animated object starts from the values it shows at the frame. The object's own constraints are left out of the space it moves in, except those Blender keeps: Follow Path, Clamp To, Child Of on all three location axes, Copy Transforms mixed Before or Before Full when moving or rotating, and when rotating Copy Rotation mixed Before or Offset and Copy Transforms mixed Before Split. It shows exactly the values confirming stores and the keys it inserts, with auto keying and without. When a dependency cycle runs through an object the preview evaluates anew (its values, its matrix or its armature's pose, also a cycle inside the pose of an armature the move reaches through another bone) or through data a moved object drives, what the scene shows depends on the order objects are evaluated in (by name): the preview then evaluates the whole scene in that order at every pointer move, as the viewport does once confirmed. An object that the cycle leaves without a matrix in that evaluation stays where the viewport drew it until the transform is confirmed. Geometry that depends on a moved object (the bones of an armature whose pose follows it, the meshes an armature deforms, modifiers) is drawn anew once confirmed. A rigid body the simulation moves (after the rigid body world's start frame) starts a transform where the simulation shows it, as in Blender, which reads its location and rotation from the simulated matrix (here taken into its parent's space, which Blender leaves out); while it is transformed it follows its channels, confirming stores where it is put and cancelling keeps its channels. The stored location and rotation are where the simulation starts the body, so the editor simulates it again from the start frame and at the current frame shows where the new simulation has it (Blender shows its cached simulation until the cache is reset at the start frame). The Snap menu adds the offset from where the simulation shows such a body to its channels, as Blender's does. A rotation keeps the scale, also of the child of an unevenly scaled parent, which changes shape as it turns, and is stored as the Euler angles closest to the previous ones (170° + 20° gives 190°, 720° + 10° gives 730°, Y can stay beyond ±90°); in gimbal lock (Y at ±90°) Z is set to 0, give or take whole turns, and X takes the rest, also by a rotation by 0, as in Blender, which does this already within 0.00215° of ±90°. A rotation by more than 180° at once (typed, or dragged further around) is one rotation by that angle, as Blender's `transform.rotate` run with a value: R X 270 of an unrotated object gives X −90°, where Blender's interactive Rotate follows the turn and gives 270°. A scale keeps the rotation and multiplies the scale of each of the object's axes by how much it stretches that axis, negated where the stretched axis points against the unstretched one, as Blender's Scale does: S −1 along X and Y of an unrotated object gives [−1, −1, 1]; of an object turned 30° about Z, S X 2 gives [1.803, 1.323, 1] and S X −1 gives [−1, 1, 1], which is not its mirror image along the global X axis. Set Origin moves the location by the offset turned and scaled by the object's rotation and scale (location + R·S·offset), as Blender does, keeping its rotation, scale and any shear, and Duplicate with an offset moves the copy as a Move does. Set Origin and Apply Transform read an animated object's values at the current frame, as Blender's channels hold them. An animated channel they change keeps its keys and is keyed at the current frame with its new value, so nothing moves there; at its other keyframes the geometry shows moved by the change (by the opposite of the origin's move, or by the applied transform once more). Blender keeps the new value without a key until the frame changes; from then on its keys decide at every frame. Parenting and clearing a parent with Keep Transform (also Armature Deform and Bone parenting, and the children of a deleted object), the children of objects whose transform is applied or whose origin is set, and Align Active Camera to View set a world matrix and store only the channels it changes relative to the parent as the scene shows it at the current frame: a rotation as the Euler angles closest to the previous ones, scales with their previous signs where the matrix allows it (a mirroring matrix flips one sign, or all three, whichever keeps the rotation closest; negative factors along two axes turn the rotation by 180° instead), and a sheared matrix (a child turned under an unevenly scaled parent) without the shear. The children and the camera key an animated channel this changes at the current frame with its new value, on the turn the channel shows there; parenting does not, so an animated channel of the child goes on showing its keys. When parenting, Blender keeps the child's channels and stores the inverse of the new parent's matrix in the child, which this editor does not have; with Keep Transform it first sets the channels from the child's world matrix, with the smallest Euler angles and, for a mirroring matrix, all three scales negated: X 190° becomes −170°. ## Modifiers

Modifiers work on meshes and on curve and text objects (on the generated surface, or on the wire of
a curve without one, so Screw revolves a profile curve). Stack operations: `object.modifier_add`,
`object.modifier_set`, `object.modifier_remove`, `object.modifier_apply`, `object.modifier_copy`,
`object.modifier_move_up`/`_down`/`_to_index`, with viewport, render and edit-mode toggles. Every
type's parameters use Blender's names and are validated (MCP: `list_modifier_types`). A parameter
that names an object takes the types Blender stores there: a mesh for the Boolean `object`, the
Array `start_cap` and `end_cap` and the Shrinkwrap `target`, an armature for the Armature
`object`, a curve for the Curve `object` (the others take any object); `object.modifier_add` and
`object.modifier_set` refuse an object of another type (code `INVALID_PARAMS`), as do MCP
`add_modifier` and `update_modifier` on a curve or text object, and the object pickers of the
Modifiers tab list only objects of those types.

As in Blender, a modifier that can do nothing with its parameters is disabled (Blender's
`is_disabled`): a Boolean, Shrinkwrap, Armature or Curve modifier without an object of the type it
needs (a mesh, an armature, a curve), an Array whose start or end cap is not a mesh, a Subdivision
Surface with 0 levels for the mode (`levels` in the viewport, `render_levels` in renders), a Bevel
of width 0, a Displace of strength 0 or along `RGB_TO_XYZ` without a texture, a Smooth or Cast with
factor 0 or no axis. The viewport, renders and Convert leave it out without an error, and
`object.modifier_apply` refuses it ("Modifier is disabled, skipping apply", code `FAILED`) and
keeps it. The Modifiers tab draws its header red when the viewport leaves it out, with the reason as
its tooltip (Blender draws its icon red), and MCP `get_scene` lists it among the `problems`, after
the errors (`disabled: true`, and `viewport: true` when only the viewport leaves it out: a
Subdivision Surface with 0 `levels` and `render_levels` above 0, which renders use). A modifier can
still name an object of another type when the object changed type afterwards (a curve converted to
a mesh) or in an older project; it is disabled then too.

`object.modifier_apply` bakes the stack up to and including the given modifier into the mesh and
removes the applied modifiers, where Blender applies only the given modifier, to the mesh without
the modifiers before it, and keeps those. Modifiers before it that are hidden in the viewport or
disabled are skipped and kept. The given modifier is applied also when it is hidden in the
viewport, as in Blender, which turns it on for the Apply.

## Constraints

Object constraints are evaluated in a per-frame dependency graph: dependencies are evaluated first,
and constraints that would form a cycle (an object tracking its own child, two objects copying each
other) are skipped and reported with the objects of the loop (`constraint.describe`, MCP
`get_scene` problems, the Constraints tab).

Exports default to every object visible in renders, evaluated at the current frame with
modifiers applied (export operators: `use_selection`, `apply_modifiers`, and `bake_resolution`
for `export_scene.gltf`; MCP `export_scene`: `objects`, `apply_modifiers`, `frame`,
`bake_resolution`). The REST download `GET /api/projects/:id/export` uses the scene's
`frame_start` unless it is given a `frame`. MCP and REST exports run in a server render process,
so a long glTF export does not hold up editors and agents, and one that needs more memory than a
render process has fails with code `OUT_OF_MEMORY` (REST: status 507) without stopping the server.
`warnings` (MCP `export_scene`, the export operators' reports) list what a format cannot represent.
Imports through MCP (`import_model`, the `import_*` operators) run in the server's process: one
that would not fit into its memory, counted from the file (a glTF file by the meshes its JSON makes
the importer decode, also where meshes share accessors, by its nodes, keyframes and embedded
images; a PLY file by its elements; an STL file by its triangles; an OBJ file by its size, meshes
(every object a copy of the vertices it uses) and objects), fails with code `OUT_OF_MEMORY` and
says how a browser editor that has the project
open runs it in its own memory (`editor_command` `run_operator` with the file in base64). One after
which the project would keep more than the server keeps for one project (its meshes, objects,
keyframes and images), or all open projects more than it keeps for all of them (the refusal names
the others), counting what a save takes for a moment, says what to lower or delete instead: the
server would hold what a browser editor imports too. The same holds for every operator run on the
server, keyframe bakes (`anim.bake_transforms`, `rigidbody.bake_to_keyframes`) by the keyframes they
write and the copies of the scene's animation they read at every frame, and operators that write
vertex groups or shape keys (parenting to an armature with weights, the `object.vertex_group_*` and
`object.shape_key_*` operators, a bone rename) by all the groups or keys of the mesh, which every
such write copies and stores again. The frames a rigid body
cache keeps count with what its project keeps (`rigidbody.cache_free` frees them), and a rigid
body simulation the server would not have the memory for, alone or with the other open projects,
is not stepped: `get_scene` lists why as the rigid body world's problem.

## Not implemented

In one place, the major Blender areas this editor does not have:

- **Node systems:** Geometry Nodes, shader nodes, the compositor, texture and world nodes.
- **Other object types and editors:** Grease Pencil, metaballs, NURBS surfaces, lattices, volumes,
  point clouds, hair curves, light probes, speakers; the video sequencer, motion tracking and
  masking, the Graph Editor, the NLA, the Image and Text editors, the Spreadsheet and the Asset
  Browser.
- **Interactive modes:** Pose Mode and armature or curve Edit Mode (bones and spline points are
  edited numerically in the Properties editor and by operators), Weight Paint (weights come from
  operators and automatic weights), Texture Paint, and editing UVs in the UV editor.
- **Simulation:** cloth, soft body, fluid, smoke and fire, dynamic paint, ocean, force fields,
  particle dynamics and hair, rigid body constraints.
- **Modeling:** knife, bisect, rip, slide, grid fill, remeshing, multiresolution, dynamic
  topology, the skin modifier and the other modifiers listed under [Modifiers](#modifiers).
- **Rendering:** GPU rendering, an Eevee-style engine, volumes, subsurface scattering, glass
  (refractive) caustics, motion blur, render passes and view layers, video output.
- **Data and extensibility:** Python scripting and add-ons, `.blend` files, library linking and
  appending, FBX, USD and Alembic.
